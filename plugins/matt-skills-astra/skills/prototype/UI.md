# UI prototype

Use real layout constraints, representative data density, and the existing component library to make a UI choice judgeable.

When the user requests alternatives, make them structurally different: layout, hierarchy, or primary interaction, not just color. Use as many as the decision needs. One requested mockup need not become three variants.

A development-only variant switcher on the existing route can help comparison. Preserve its normal behavior when no prototype is selected. Alternatively, use an isolated preview if modifying the live route would create risk. Keep mutations stubbed and protect production from prototype-only behavior.

Provide a usable preview and explain what each option tests. Check relevant responsiveness and interactions. Selection of a design does not itself authorize deploying it; integrate and remove alternatives only when requested, preserving user work.
