# Issue tracker: GitHub

Use the repository's connected GitHub tools or gh CLI. Verify the owner/repository from context and remotes, especially inside a fork; avoid silently posting to upstream.

Read issues, comments, labels, and relevant PR diffs for the requested scope. Prefer JSON for structured queries and verify command fields against available help. A bare number may identify an issue or a PR.

Creation, comments, labels, assignment, closing, and dependency changes require the corresponding user intent. Use body files or safely structured tool arguments for multiline content, respecting the host shell.

For a Wayfinder map, use an existing project convention or a parent issue with linked children. Native sub-issues and dependencies can help when supported; otherwise use explicit links and blocker lists. Verify any native endpoint before writing.

A child is ready only when the required blocker outcomes are satisfied, not merely because their issues are closed. Claim work only under the collaboration convention and authorized scope. Record evidence when resolving a ticket and preserve historical decisions.

A missing tracker configuration does not prevent a local draft.
